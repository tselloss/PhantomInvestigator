# Design decisions log

Record every non-obvious choice here as you make it. This file = interview prep.

| Date | Decision | Alternatives considered | Why |
|---|---|---|---|
| 2026-07-06 | No agent framework (raw API + hand-written loop) | LangChain, LlamaIndex | Learn the fundamentals; full control; better interview story |
| 2026-07-06 | pgvector over dedicated vector DB | Qdrant, Pinecone | One less service; Postgres skills transfer; scale is tiny |
| 2026-07-06 | Fault injection doubles as "deploys" | Real git history | Perfect ground truth for evals with zero extra infra |
| 2026-07-07 | Fork AIInvestigator into PhantomInvestigator rather than extend it in place | Add real-source tools directly to AIInvestigator | AIInvestigator stays a clean, self-contained portfolio demo; PhantomInvestigator can carry real credentials, webhooks, and prod-facing risk without touching that |
| 2026-07-07 | Keep demo-app/Prometheus/Loki/Grafana stack in PhantomInvestigator | Strip it down to only real integrations | Lets the agent loop be regression-tested against synthetic faults without needing live prod access |
| 2026-07-07 | Jira webhook auth via shared secret query param, not signature | Jira Cloud has no native payload signing | Practical given the platform constraint; document as a known limitation vs. GitHub's HMAC |
| 2026-07-11 | Azure DevOps auto-investigate via inbound Service Hook (webhook), not a polling loop | Background poller on a timer | Matches the existing Jira/GitHub pattern exactly (same secret-in-query-param auth as Jira, since ADO service hooks don't sign payloads either); app has zero scheduler infra today, so a poller would be new machinery for one source instead of reusing what's proven |
| 2026-07-11 | Deployment matched to an ADO webhook event by "{org}/{project}" on deployments.azure_devops_project, not by resourceContainers.project.id | Decrypt every client's stored ADO credential and compare org/project (client-level, not deployment-level) | Mirrors jira_project_key/github_repo exactly -- one column, one find_deployment_by_* lookup, no per-event decryption fan-out; ADO payloads reliably carry org (in resource.url) and project name (System.TeamProject field), just not as a single ready-made key |
| 2026-07-11 | post_azure_devops_comment removed as an LLM-callable tool; posting is now always a queued pending_action requiring operator approval | Keep it callable but only wire the approval gate for webhook-triggered runs | Jira never exposed a callable post tool at all -- posting only ever happened via the approval queue. Since the user asked for Jira-equivalent approval-gating once ADO investigations can fire unattended from a webhook, an LLM-callable tool that bypasses the gate on any *other* trigger (manual, future sources) would defeat the point |
| 2026-07-11 | Auto-fix PR proposals stored in a second, independent `pending_fix_action` column rather than folding into `pending_action` as a list | Rewrite `pending_action` into a list of typed actions | A code-fix approval and a ticket-comment approval are genuinely independent (either, both, or neither may apply to one run) and there will only ever be two kinds -- a list rewrite would touch `finish()`, both resolve functions, both routes, the UI's type-switch, and every existing jira_comment/azure_devops_comment test for no real benefit. Two columns keep that entire existing contract byte-for-byte unchanged |
| 2026-07-11 | proposed_fix_files entries are rejected wholesale (not trimmed file-by-file) unless every path was read via get_file_contents this run, tracked by a new `files_read` set in loop.py rather than reconstructed from the stored trace | Reconstruct "was this file read" from `investigations.trace` | trace is `NULL` for every webhook-triggered run (`run_agent()` never collects one) and even when present, tool_result is hard-truncated to 500 chars -- nowhere near a real file. A silently truncated "complete" file is exactly what makes an LLM-authored file replacement dangerous, so get_file_contents also never truncates (unlike every other read tool), erroring past a size cap instead. A partial multi-file fix is worse than none since the operator can't tell it's partial from the diff alone, hence whole-proposal rejection over per-file trimming |
| 2026-07-11 | Auto-fix PR target branch is a per-deployment allowlist (`deployments.allowed_base_branches`, opt-in/NULL by default) re-validated live at approve time, not a free-text field or a snapshot from proposal time | Let the operator type any branch at approval time; trust the branch list captured when the proposal was built | This is the first capability that writes to a customer's repo rather than a ticket, so the allowlist is the actual authorization boundary -- an operator could edit it between proposal and approval, so approve-fix re-fetches the deployment live rather than trusting anything cached in pending_fix_action |
