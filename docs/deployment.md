# Deploying PhantomInvestigator

Target: the same server that already hosts ClinicOps, at **phantominvestigator.com**.
There is no automated deploy pipeline for this yet (see `docker-compose.prod.yml`'s
comment header and the README's Build status table) -- this is a manual runbook.

## Step 0 -- find out what's actually running on that server

`scripts/clinicops/checkin.env.example` mentions ClinicOps's own CI "already
triggers a VPS/Coolify/Dokku webhook" without saying which. Before doing
anything else, SSH in and check:

```bash
docker ps
which coolify 2>/dev/null || coolify version 2>/dev/null
which dokku 2>/dev/null || dokku version 2>/dev/null
ls /etc/nginx/sites-enabled/ 2>/dev/null; caddy version 2>/dev/null
ls /opt
```

- **Plain Docker + a reverse proxy (nginx/Caddy) or nothing yet** -- follow
  "Plain Compose" below. This is the most likely case, since ClinicOps's own
  `docker-compose.yml` pattern (per this repo's `scripts/clinicops/`) suggests
  plain Docker Compose rather than a PaaS.
- **Coolify** -- follow "Coolify" below.
- **Dokku** -- follow "Dokku" below; this one needs a bit more work since
  Dokku doesn't run `docker-compose.yml` sidecars (Postgres/Langfuse) natively.

## Env checklist (all cases)

Copy `.env.example` to `.env` on the server and fill in, at minimum:

- `SESSION_SECRET`, `CREDENTIALS_ENCRYPTION_KEY`, `POSTGRES_PASSWORD` -- generate with the commands already commented above each var in `.env.example` (or run `scripts/setup.sh`, which auto-generates all of these).
- `GOOGLE_REDIRECT_URI=https://phantominvestigator.com/auth/google/callback` (only if Google sign-in is wanted -- update the redirect URI in Google Cloud Console to match).
- `JIRA_WEBHOOK_SECRET`, `GITHUB_WEBHOOK_SECRET`, `AZURE_DEVOPS_WEBHOOK_SECRET` -- whatever you'll configure on the Jira/GitHub/Azure DevOps side (see "Re-point webhooks" below).
- All `LANGFUSE_*` secrets (also auto-generated by `scripts/setup.sh`).
- Your AI provider key: leave `ANTHROPIC_API_KEY`/`AI_API_KEY` blank in `.env` and set it from the running app's Settings page after you register the first account instead (existing project convention -- see CLAUDE.md).
- `SESSION_COOKIE_SECURE=true` -- already the default; requires TLS in front of the app (Caddy/nginx/Coolify/Dokku all provide this).

## Plain Compose (Caddy)

```bash
git clone <this-repo-url> /opt/phantom-investigator   # or your usual deploy path
cd /opt/phantom-investigator
cp .env.example .env && $EDITOR .env                  # fill in the checklist above
scripts/deploy/deploy.sh                               # pulls, builds, starts, waits for healthy
```

If nothing already listens on ports 80/443 on this host:

```bash
sudo cp scripts/deploy/Caddyfile.example /etc/caddy/Caddyfile
$EDITOR /etc/caddy/Caddyfile   # confirm the domain
sudo systemctl reload caddy
```

If nginx (or another proxy) already fronts ClinicOps on this host, add a
server block instead of installing Caddy:

```nginx
server {
    listen 443 ssl;
    server_name phantominvestigator.com;
    # ... your existing TLS cert config ...
    location / {
        proxy_pass http://localhost:8085;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

Re-run `scripts/deploy/deploy.sh` for every future deploy (it rebuilds the
image -- `agent/` is not volume-mounted, so a plain `git pull` alone does
nothing until the image is rebuilt).

## Coolify

1. New Resource -> Docker Compose, point it at this repo, compose file `docker-compose.prod.yml`.
2. Set the env vars from the checklist above in Coolify's environment editor (not a committed `.env`).
3. Set the domain to `phantominvestigator.com` -- Coolify's built-in Traefik handles TLS automatically.
4. Deploys happen through Coolify's UI/webhook instead of `scripts/deploy/deploy.sh`; the underlying command is the same `docker compose -f docker-compose.prod.yml up -d --build`.

## Dokku

`agent/Dockerfile` builds the whole app (UI baked in) as a single image, so
`dokku apps:create phantominvestigator` + push-to-deploy works for the `agent`
service itself. The compose-only services (Postgres, Langfuse) aren't
covered by a plain Dokku app -- either install the Dokku Postgres plugin and
point `DATABASE_URL` at it, or keep running `postgres`/Langfuse via
`docker compose -f docker-compose.prod.yml up -d postgres langfuse-worker
langfuse-web clickhouse minio redis langfuse-postgres` alongside the Dokku
app. Confirm this is really the platform in use (Step 0) before investing
time here -- flagged as a follow-up to work out once confirmed.

```bash
dokku apps:create phantominvestigator
dokku domains:add phantominvestigator phantominvestigator.com
dokku config:set phantominvestigator SESSION_SECRET=... CREDENTIALS_ENCRYPTION_KEY=... # ...rest of the checklist
git remote add dokku dokku@<server>:phantominvestigator
git push dokku main
```

## Re-point webhooks

Once the app is live at `https://phantominvestigator.com`, update each
integration to stop pointing at the local `ngrok` tunnel:

- **Jira**: Project settings -> System -> WebHooks -> `https://phantominvestigator.com/webhooks/jira?secret=<JIRA_WEBHOOK_SECRET>`
- **GitHub**: Repo settings -> Webhooks -> `https://phantominvestigator.com/webhooks/github`
- **Azure DevOps**: Project settings -> Service Hooks -> `https://phantominvestigator.com/webhooks/azure_devops?secret=<AZURE_DEVOPS_WEBHOOK_SECRET>`

## Post-deploy smoke test

1. `curl https://phantominvestigator.com/health` -> `{"ok": true, "version": "..."}`.
2. Register an account, confirm login works.
3. Confirm the Terms of Service gate is actually enforced server-side: a fresh session that hasn't accepted terms gets `403` from any `/api/*` call, and succeeds after `POST /auth/accept-terms`.
4. Trigger one real investigation (via a live Jira/GitHub webhook or the manual "Investigate" button) end-to-end and confirm a trace shows up in the self-hosted Langfuse instance.
5. Redeploy once (`scripts/deploy/deploy.sh` again) and confirm existing clients/investigations/users are still there -- `pgdata` is a named Docker volume, so it survives `up -d --build`, but not `down -v` or host loss.

## Backups (follow-up, not blocking the first deploy)

`pgdata` (app data) and `langfuse_postgres_data`/`langfuse_clickhouse_data`
(traces) are named volumes with no backup today. A `pg_dump` timer mirroring
the existing `scripts/clinicops/checkin.timer` pattern (systemd timer +
oneshot service) would be a natural fit once the deploy itself is stable.
