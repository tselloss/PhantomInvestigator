# Deploying PhantomInvestigator

Target: the same server that already hosts ClinicOps, at **phantominvestigator.com**.
There is no automated deploy pipeline for this yet (see `docker-compose.prod.yml`'s
comment header and the README's Build status table) -- this is a manual runbook.

## Platform (confirmed)

Checked ClinicOps's own repo directly rather than guessing: it's a **plain VPS,
SSH-deployed, plain Docker Compose** -- no Coolify, no Dokku. Evidence:
`docs/github-secrets.md` there states env vars are "injected into the
container at deploy time via SSH"; its `SSH_HOST`/`SSH_USER`/`SSH_PRIVATE_KEY`
GitHub secrets are set while `DEPLOY_WEBHOOK_URL` (the Coolify/Dokku option
in its CI comments) is not; its `Makefile` just runs `docker compose up -d
--build`. Its `app` service also runs behind *some* reverse proxy (comment:
"required when running behind Docker/proxy") -- which one (nginx vs Caddy)
isn't recorded in that repo since it's host-level config, so
`scripts/deploy/setup-proxy.sh` (below) detects it automatically instead of
requiring a manual check.

## Env checklist

Copy `.env.example` to `.env` on the server and fill in, at minimum:

- `SESSION_SECRET`, `CREDENTIALS_ENCRYPTION_KEY`, `POSTGRES_PASSWORD` -- generate with the commands already commented above each var in `.env.example` (or run `scripts/setup.sh`, which auto-generates all of these).
- `GOOGLE_REDIRECT_URI=https://phantominvestigator.com/auth/google/callback` (only if Google sign-in is wanted -- update the redirect URI in Google Cloud Console to match).
- `JIRA_WEBHOOK_SECRET`, `GITHUB_WEBHOOK_SECRET`, `AZURE_DEVOPS_WEBHOOK_SECRET` -- whatever you'll configure on the Jira/GitHub/Azure DevOps side (see "Re-point webhooks" below).
- All `LANGFUSE_*` secrets (also auto-generated by `scripts/setup.sh`).
- Your AI provider key: leave `ANTHROPIC_API_KEY`/`AI_API_KEY` blank in `.env` and set it from the running app's Settings page after you register the first account instead (existing project convention -- see CLAUDE.md).
- `SESSION_COOKIE_SECURE=true` -- already the default; requires TLS in front of the app, which the proxy setup below provides.

## Deploy

```bash
git clone https://github.com/tselloss/PhantomInvestigator.git /opt/phantom-investigator
cd /opt/phantom-investigator
cp .env.example .env && $EDITOR .env          # fill in the checklist above
sudo scripts/deploy/setup-proxy.sh             # detects nginx/Caddy/neither, configures phantominvestigator.com
scripts/deploy/deploy.sh                       # pulls, builds, starts, waits for the agent healthcheck
```

If `setup-proxy.sh` installed nginx's config (i.e. nginx was already running
on this host), finish TLS with `sudo certbot --nginx -d
phantominvestigator.com`. If it used/installed Caddy, TLS is automatic --
nothing further to do.

Re-run `scripts/deploy/deploy.sh` for every future deploy (it rebuilds the
image -- `agent/` is not volume-mounted, so a plain `git pull` alone does
nothing until the image is rebuilt). `setup-proxy.sh` only needs to run once.

## Re-point webhooks

Once the app is live at `https://phantominvestigator.com`, update each
integration to stop pointing at the local `ngrok` tunnel:

- **Jira**: Project settings -> System -> WebHooks -> `https://phantominvestigator.com/webhooks/jira?secret=<JIRA_WEBHOOK_SECRET>`
- **GitHub**: Repo settings -> Webhooks -> `https://phantominvestigator.com/webhooks/github`
- **Azure DevOps**: Project settings -> Service Hooks -> `https://phantominvestigator.com/webhooks/azure_devops?secret=<AZURE_DEVOPS_WEBHOOK_SECRET>`

## Post-deploy smoke test

1. `curl https://phantominvestigator.com/health` -> `{"ok": true, "version": "..."}`.
2. Register an account, confirm login works.
3. Confirm the Terms of Service gate is actually enforced server-side: a fresh session that hasn't accepted terms gets `403` from any `/api/*` call, and succeeds after `POST /auth/accept-terms`.
4. Trigger one real investigation (via a live Jira/GitHub webhook or the manual "Investigate" button) end-to-end and confirm a trace shows up in the self-hosted Langfuse instance.
5. Redeploy once (`scripts/deploy/deploy.sh` again) and confirm existing clients/investigations/users are still there -- `pgdata` is a named Docker volume, so it survives `up -d --build`, but not `down -v` or host loss.

## Backups (follow-up, not blocking the first deploy)

`pgdata` (app data) and `langfuse_postgres_data`/`langfuse_clickhouse_data`
(traces) are named volumes with no backup today. A `pg_dump` timer mirroring
the existing `scripts/clinicops/checkin.timer` pattern (systemd timer +
oneshot service) would be a natural fit once the deploy itself is stable.
